# 設計書・ドキュメントの更新先マップ

このプロジェクトは「実装したら対応するドキュメントも同じタイミングで更新する」運用。
何をやったかによって更新すべきファイル・節が変わる。

## ドキュメント一覧と更新トリガー

| ファイル | 内容 | 更新するタイミング |
|---|---|---|
| `README.md`(リポジトリ直下) | ポートフォリオ的な概要(コアループ・機能一覧・システム構成・技術スタック)。詳細は仕様概要書・設計書へリンクする。実装状況は書かない(`progress.md`が正) | コアループや機能構成が変わったとき、技術スタックが変わったとき(いずれも頻度低) |
| `Shared/docs/game-spec.md` | 仕様概要書。ゲームの内容とルール(遊びの流れ・パチモン・育成・スカウト・ショップ・対戦・ジェム・チャット)。API・DB・クラス名は書かない | ゲームのルール・数値(確率・報酬・制限時間等)・画面の流れを変えたとき。未実装/追加予定の表記を実装に合わせて外すとき |
| `Shared/docs/design.md` | 設計書。1章 全体構成、2章 共通の決まり(命名・ID・nullable・`playerDiff`・アイテム)、3章 APIサーバー(API一覧と各API)、4章 DB、5章 マスターデータ、6章 クライアント、7章 バトルサーバー、8章 未確定の論点 | API・DB・マスタ・クライアントの層構成・バトルサーバーの進行を実装・変更したとき(下のチェックリスト) |
| `Shared/docs/progress.md` | 開発進捗・実装状況・残タスク一覧(生きたステータス文書) | 何か1つの作業単位を終えるたびに(ほぼ毎回) |
| `Shared/docs/proposals/*.md` | 他リポジトリへ移す予定の設計や将来の構想(gRPC基盤・画面遷移パッケージ・BootLoader・HTTPS等) | その構想自体の方針を変えたときのみ |
| `Shared/docs/notes/*.md` | 学習・経緯のメモ(api-codegenの経緯、cargoのコマンド等) | 原則更新しない(記録として残す) |
| `DEVELOPMENT.md` | 環境構築・起動手順・環境変数・トラブルシューティング | 環境変数・起動手順・必要なツールを変えたとき |

## 実装タスクを終えたときのチェックリスト

1. **API(エンドポイント)を追加/変更した**
   → `design.md`「3.3 API一覧」の表と、該当する「3.x」節(リクエスト/レスポンス・検証・エラー)を更新
   → `playerDiff`を返すAPIなら「2.4 所持データの差分(`playerDiff`)」の表にも追加
   → 内部API(BattleServer用)なら「3.9」と、バトルサーバー側の「7.5 APIサーバーとの連携」
   → 実装状況は`progress.md`のAPI一覧表を更新
2. **マスターデータのテーブル/Enumを追加した**
   → `master-data-schema-add` スキル完了後、`design.md`「5.2 テーブル」に追記(配布先が限られるなら「5.1」も)
3. **DBスキーマ(マイグレーション)を変更した**
   → `design.md`「4.2 テーブル一覧」と、該当する「4.x」のテーブル定義を更新
   → マイグレーションのSQLファイル内のコメントは、適用済みなら書き換えない(sqlxのチェックサムが変わるため)
4. **Client側の層構成・クラス構成を変更した**
   → `design.md`「6. クライアント」の該当節を更新。削除/改名したクラス名が説明文・表に残っていないか`grep`で確認する
5. **バトルの進行・通信契約・BattleCoreを変更した**
   → `design.md`「7.2 Atlas.BattleCore」「7.3 通信契約」「7.4 対戦の進行」、Client側なら「6.8 バトル画面」
6. **ゲームのルール・数値・画面の流れを変えた**
   → `game-spec.md`の該当章。機能を実装し終えたら「(未実装)」「(追加予定)」の表記を外す
7. **決まっていないことが残った**
   → `design.md`「8. 未確定の論点」(仕様の未確定は`game-spec.md`の該当節の「未確定」)
8. **どの作業でも共通**
   → `progress.md` の該当セクション(クライアント / APIサーバー / バトルサーバー / 共通 の「実施済み」「TODO」)を更新する。
     「実装したつもりが別の層(DB投入やキャッシュ)が追いついていない」ようなギャップを見つけたら、`progress.md`の
     該当領域の「TODO」にタスク(タイトル+詳細)として明記しておく — 実装漏れの再発見コストを下げるための運用

## 書き方の流儀

- 設計書には「何を・なぜ」を書き、型・メソッドの定義そのものはソースを正とする(ソースを丸写ししない)
- 経緯(「以前は〜だった」)は書かない。判断の理由として残す価値があるものは「採用しなかった案」として書く
- 「検討したが採用しなかった案」は理由と共に、該当する節の末尾に残す
- 同じ内容を複数の節に書かない。用語・命名規則は`design.md`「2. 共通の決まり」が正で、他の節からは参照する
- 実装状況は表(メソッド/パス、または `[x]`/`[ ]` チェックボックス)で`progress.md`に書く
- コードのコメント(C#・Rust・SQL・YAML)からドキュメントを指さない。ドキュメントの構成を変えてもコードを直さずに済むよう、
  コメントには実装の概要とコードから読み取れない注意点を書く(ルートのCLAUDE.md「コメント」)
